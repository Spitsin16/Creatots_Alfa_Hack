# AGENTS.md — инструкции для ИИ-агентов (Codex, Claude Code) и людей

Проект: **умный кредитный кабинет МСБ** для хакатона «Альфа-Будущее» (кейс «Умный кредитный кабинет предпринимателя»).
Сдача онлайн-этапа — **26.10.2026**. Проверяющие сами запускают решение по README на машине ~12 ГБ RAM без GPU.

## Объём MVP в двух абзацах

Только **действующие клиенты Альфы** (ИП и ООО), сегменты 1А, 1Б, 2А, 2Б, 3А, 3Б. Клиент: вход → согласие на БКИ/ФНС (одна галочка) → анкета (ТЗ 5.2) → предложение с объяснением «почему такая сумма» и «как получить больше» → заявка → трекер статуса → решение → подписание кодом → симулированная выдача. Связь с сотрудником — чат по заявке, звонков нет, SMS — только заглушка с записью в журнал.

Банк (`/bank`): очередь, карточка заявки с факторами, действия андеррайтера с обязательным кодом причины, второе одобрение риск-менеджера выше 5 млн, админ правил (версии `rules.yaml`), журнал аудита. Модули кабинета (после сквозного прогона): прогноз кассового разрыва, сезонный график, ассистент, хранилище документов — каждый за флагом.

## Стек и структура

- Фронт: React + TypeScript + Vite, React Router, TanStack Query, клиент API генерируется из OpenAPI.
- Бэк: Python 3.12, FastAPI, SQLAlchemy 2, Alembic, Pydantic 2, httpx. Воркер — тот же код, отдельный процесс, задачи из таблицы `outbox`.
- БД: PostgreSQL 16. Моки внешних систем: отдельный FastAPI-сервис.
- LLM (опционально): любой **OpenAI-совместимый API** через `LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL`; по умолчанию Ollama + Qwen2.5-7B-Instruct. **Без LLM всё должно работать** (шаблоны).

```
backend/          # FastAPI: app/api, app/models, app/services, app/worker, alembic/, tests/
  app/services/   # scoring/, segments/, statement_1c/, forecast/, seasonal/, explain/, notifications/
mocks/            # отдаёт data/personas по ИНН: /alfa /registry /fns /bki /mchd (+ ?fail=timeout|500)
frontend/         # React SPA: кабинет клиента и /bank
data/             # правила, персоны, выписка, эталон — НЕ генерировать заново без причины
docs/             # TZ.md, PROGRESS.md, ARCHITECTURE.md, STATES.md, DATA_MODEL.md, DECISION_RULES.md, ASSUMPTIONS.md, RESEARCH.md
docker-compose.yml
.env.example

```

## Команды (текущий этап)

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r backend/requirements.lock
(cd backend && python -m pytest -q)           # тесты бэка
(cd backend && ruff check .)                  # линтер
(cd backend && alembic upgrade head)          # миграции (нужен DATABASE_URL)
(cd backend && python -m app.seed)            # синтетические данные и rules_v1
python data/reference/engine.py data/rules.yaml data/personas --json data/reference/expected.json  # пересчитать эталон
```

Последняя команда запускается из корня репозитория. Для локальной проверки можно использовать `DATABASE_URL=sqlite:///./credit-dev.db`; CI проверяет миграцию на PostgreSQL 16. Docker Compose, воркер и фронт ещё в работе; актуальный статус — в `docs/PROGRESS.md`.

## Обязательные правила

1. **Скоринг сверяется с эталоном.** `backend/tests/test_reference.py` прогоняет каждую персону со сценарием `persona.scenario` и сравнивает с `data/reference/expected.json`: `cls`, `score`, `factors`, `product`, `outcome`, коды советов — точно; `limit`, `rate`, `payment` — с допуском ±10 000 ₽ / ±0,01 п.п. Тест красный — не мержим.
2. **Не меняй числа в `data/rules.yaml` без пересчёта эталона** в том же коммите. p2b и p_stop стоят ровно на границе класса D (45 баллов) — после любой правки весов проверь их исход.
3. **Правила читаются из БД (версия `rules_v1` из `rules.yaml`), а не захардкожены.** Каждое решение хранит `rules_version`.
4. **Статусы — только через state machine** (ТЗ раздел 8). Недопустимый переход → HTTP 409. Каждый переход пишется в `status_history` в той же транзакции.
5. **Деньги — целые копейки (`bigint`)**, ставки — `Decimal`/`numeric(5,2)`, даты — `timestamptz`. «Сегодня» в демо задаётся `DEMO_TODAY=2026-10-22`.
6. **Клиенту не отдаём баллы, пороги и правила антифрода** — только факторы словами, цифры клиента и советы. Отказ без кода причины API не принимает (422).
7. **Никаких платных API, реальных SMS, реальных интеграций и реальных персональных данных.** Внешние системы — только через сервис `mocks`.
8. **LLM никогда не обязателен и не принимает решений.** Он только формулирует текст по готовым фактам; все числа в ответе проверяются против входа; таймаут 10 с → шаблон.
9. **Зависимости — только с lock-файлами** (`backend/requirements.lock`, `package-lock.json`) и записью в `THIRD_PARTY_NOTICES`.
10. **Маленькие коммиты** с префиксами `feat:`, `fix:`, `test:`, `docs:`, `chore:`. Жюри смотрит историю — не сливай день работы одним коммитом.

Нужно поменять чужую область — договорись или сделай отдельный PR с понятным описанием. Сервисы движка — чистые функции без доступа к БД: на вход данные, на выход результат; API и воркер их вызывают.

## Ветки и передача смены

- `main` — всегда запускается. Работа — в ветках `feat/<область>-<что>`, вливаем через PR с зелёным CI.
- **Перед тем как остановиться** (кончаются лимиты, конец дня): обнови `docs/PROGRESS.md` — что сделано, что в работе (ветка, файл, на чём остановился), что сломано, следующий шаг — и запушь. Следующий агент начинает с чтения PROGRESS.md.
- Не оставляй незакоммиченную работу: лучше `wip:` коммит в своей ветке, чем потерянный код.

Код в `main`, тесты зелёные, `docker compose up` поднимает всё с нуля, сценарий проходит руками на нужной персоне, PROGRESS.md обновлён.
